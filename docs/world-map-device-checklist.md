## 2. 事前条件、セーブ保護、fixture

1. PRのプレビュー等、公開承認前の対象URLを使う。`main`や本番へ反映しない。ローカル確認は対象SHAをcheckoutし、リポジトリ直下で`npm run dev -- --host 0.0.0.0 --port 4173`を実行する。同じLAN上の端末から`http://<開発PCのLAN内IP>:4173/`を開く。OSのファイアウォール許可はこのポートと一時利用に限定し、インターネットへ公開しない。キャッシュを消して再読込し、対象SHAとURLを上表へ記録する。
2. 既存データがある場合は、メニュー → `💾 セーブ管理` → `セーブを書き出す`でJSONを保存する。ファイルが開け、`schemaVersion`、`instances`、`items`、`progress`があることを確認する。これを `BASELINE` とし、原本は編集しない。
3. fixture切替前にも現在のセーブを書き出す。fixtureは `BASELINE` の複製だけを編集し、`saveMeta.integrityHash`を`null`にしてから`セーブを読み込む`から取り込む。値を残したまま編集すると「整合性ハッシュの不一致」が修復・移行記録へ出るため、合格fixtureには使わない。確認ダイアログの個体数・コイン数を照合してから承認する。
4. Hard / Extreme戦の勝利確認には十分に育成したテスト用セーブを使う。戦力不足は勝利扱いにせず `B` と記録する。

## 9. 終了、rollback、復旧

1. 各fixtureの最後にゲーム内`セーブを書き出す`を実施し、結果JSONとスクリーンショットを保存する。
2. テスト終了後、`BASELINE`を`セーブを読み込む`から復元し、個体数、party、coins、主要items、チュートリアル状態を照合する。
3. 読込直後に誤データと判明した場合は、追加操作をせずメニュー → `直前のバックアップへ戻す`。復旧できなければタブを閉じ、`BASELINE`原本を再読込する。`セーブデータをリセット`は復旧手段に使わない。
4. コード不具合時は公開/mergeせず、対象SHA・fixture・証拠を添えて5Cへ戻す。データ破損疑いでは現状JSONと`修復・移行記録`を保存し、原本を上書きしない。
5. 全必須欄が`P`で証拠が揃った場合のみ、実施者が5Dを合格と記録する。公開（5F）には別途ユーザー本人の明示承認が必要。
